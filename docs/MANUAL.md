第一卷 计算机的诞生与辉煌
要理解一个操作系统,先要理解承载它的机器;要理解机器,先要理解计算本身的历史。本卷从人类最早的计数工具出发,走过机械计算、电子计算、集成电路三个时代,最终抵达操作系统诞生的门槛。

第 1 章 计算的黎明
1.1 从数手指到算盘
计算的起点是计数。人类最早用手指计数,进而用石子、结绳、刻痕记录数量。这些手段只是"记录",还不是"计算"——计算意味着对数量施加操作:加、减、乘、除。

算盘(约公元前 2400 年,巴比伦;公元 2 世纪中国定型)是第一台真正意义上的人工计算装置。算盘通过拨动算珠表示数位,操作者按口诀执行运算。它的意义在于:

将"数"物化为可操作的物理状态(算珠位置)

将"算法"固化为操作流程(口诀)

计算速度远超心算,且结果可复查

算盘确立了两个贯穿全部计算机史的思想:状态表示数值、规则驱动运算。这两点在后文的机械计算器、电子计算机中反复出现。

1.2 机械计算器:帕斯卡与莱布尼茨
1642 年,法国数学家布莱兹·帕斯卡制造了第一台机械计算器,可执行加法和减法。机器内部是齿轮系:每个齿轮代表一个十进制位,齿轮咬合进位,完成加法。

1673 年,戈特弗里德·莱布尼茨在帕斯卡的基础上增加了乘除能力(通过重复加减与移位实现),并指出二进制系统的优越性——这比图灵早了两百多年预见了二进制的逻辑基础。

机械计算器的核心结构:

数字输入(拨盘) ──▶ 齿轮寄存器(每位数一个齿轮)
进位链(相邻齿轮咬合) ──▶ 自动进位
操作手柄 ──▶ 驱动齿轮运算 ──▶ 结果读数窗
CAUTION:齿轮计算器受物理精度限制——齿轮磨损、间隙会造成误差。这个"精度困境"直到电子时代才被彻底解决。

1.3 可编程的梦想:巴贝奇与分析机
1822 年,查尔斯·巴贝奇设计了差分机,用有限差分法计算多项式,用于航海表的自动生成。差分机是纯机械的,但已经包含了"存储"与"运算"的分离。

巴贝奇真正的远见在于 1837 年设计(未建成)的分析机。分析机包含:

部件	功能	对应现代概念
存储(Mill)	保存数值	内存
运算(Store)	执行加减乘除	ALU
控制	依序执行指令	控制单元
输入/输出	打孔卡读写	I/O
分析机的关键突破是打孔卡程序——程序与数据分离,机器按卡片序列执行任意算法。艾达·洛夫莱斯为分析机编写了第一段"程序"(伯努利数计算),成为历史上第一位程序员。

分析机确立的"存储程序"思想,在一百年后由冯·诺依曼重新提出并电子化。

1.4 布尔代数与逻辑基础
1854 年,乔治·布尔出版《思维定律的研究》,将逻辑推理代数化:真/假、与/或/非可以像数字一样运算。布尔代数当时看似纯数学,却在七十年后成为数字电路的理论基石。

关键对应关系:

布尔运算	数字电路	用途
与(AND)	与门	位掩码、条件判断
或(OR)	或门	置位、合并
非(NOT)	非门	取反
异或(XOR)	异或门	比较、加密
没有布尔代数,就没有二进制电路;没有二进制电路,就没有现代计算机。这一章的知识在第二卷第 7 章(内存管理)中会以页表位的形式再次出现。

1.5 小结
算盘确立了"状态表示数值、规则驱动运算"

帕斯卡/莱布尼茨用齿轮实现机械运算,受制于物理精度

巴贝奇分析机提出存储程序与打孔卡编程,超越时代

布尔代数提供了数字电路的理论基础

第 2 章 电子时代:从 ENIAC 到冯·诺依曼
2.1 真空管与第一台电子计算机
20 世纪 40 年代,战争对弹道计算的需求催生了电子计算。真空管(电子管)取代齿轮成为基本开关元件:通/断两种状态天然对应二进制 0/1,且速度比机械部件快数千倍。

1946 年,ENIAC(电子数字积分计算机)问世:

1.8 万个真空管、7 万个电阻

每秒 5000 次加法

程序靠插拔电缆与开关配置——改程序要数天

ENIAC 的局限是程序与硬件耦合:没有可读写的存储程序,每次计算都要重新接线。

2.2 冯·诺依曼架构:存储程序计算机
1945 年,约翰·冯·诺依曼在《EDVAC 报告初稿》中提出存储程序架构,将巴贝奇的思想电子化:

内存(指令 + 数据同池存储)
  ▲            │
  │  取指/译码  ▼
控制单元 ◀──▶ 运算单元(ALU)
  ▲
  │
  └── 输入/输出
核心原则:

程序即数据:指令与数据同存于内存,程序可被改写

顺序执行:取指 → 译码 → 执行 → 更新 PC(程序计数器)

单一存储:指令与数据共用地址空间

几乎所有现代 CPU(包括 x86-64)都是冯·诺依曼架构的后裔。Gvtcier 的内核入口 0xFFFF800000000000+ 就是这一架构中"内存中既有代码又有数据"的直接体现。

2.3 晶体管:开关的微型化
1947 年,贝尔实验室的约翰·巴丁、沃尔特·布拉顿、威廉·肖克利发明晶体管。晶体管是半导体制成的电子开关,相比真空管:

维度	真空管	晶体管
体积	大(灯泡级)	极小
功耗	高,发热大	低
寿命	数千小时	极长
速度	快	更快
晶体管使"把成千上万个开关装进一台机器"成为可能——这是集成电路的前提。1956 年,三人因晶体管获诺贝尔物理学奖。

2.4 小结
真空管让电子计算成为现实,但程序与硬件耦合

冯·诺依曼提出存储程序架构,程序即数据

晶体管解决真空管的体积与功耗瓶颈,开启微型化之路

第 3 章 集成电路与微处理器
3.1 集成电路:把电路印在硅片上
1958 年,杰克·基尔比(德州仪器)与罗伯特·诺伊斯(仙童半导体)分别发明集成电路(IC):将多个晶体管、电阻、导线制作在同一块半导体衬底上。集成电路的意义:

元件间连线在制造时完成,无需人工焊接

规模扩大后单元件成本急剧下降

可靠性远超分立元件

摩尔定律(1965 年,戈登·摩尔):集成电路上晶体管数量约每两年翻一番。这一定律预言并驱动了此后六十年的计算能力增长。

3.2 微处理器:一块芯片上的计算机
1971 年,英特尔 4004 发布,是第一款商用微处理器:将 CPU 的全部功能集成于单芯片,含 2300 个晶体管,主频 740kHz。

1978 年,英特尔 8086 发布,确立 x86 架构:

16 位寄存器、20 位地址总线(可寻址 1MB)

分段内存模型(段:偏移)

向后兼容的设计思想——后代处理器必须能运行旧程序

1985 年 80386 引入 32 位保护模式与分页;2003 年 AMD64 扩展为 64 位,即今天的 x86-64。Gvtcier 目标平台 x86-64 正是这条血脉的当代形态。

3.3 从裸机到软件:为什么需要操作系统
微处理器出现后,一台计算机可以只跑一个程序——但实践中很快发现:

多个程序都要用 CPU、内存、磁盘,谁先谁后?

程序出错会破坏其他程序甚至系统?

硬件型号繁多,每个程序都直接操作硬件?

操作系统正是为解决这些问题而生:它统一管理硬件资源,向程序提供抽象接口,隔离错误。Gvtcier 的全部内容——引导、内存、调度、文件、网络——都是对这些问题的回答。

3.4 小结
集成电路让大规模元件制造成为可能,摩尔定律驱动增长

4004 开创微处理器,8086 确立 x86,AMD64 扩展至 64 位

硬件复杂化催生操作系统:统一管理、抽象接口、错误隔离

第 4 章 操作系统与软件革命
4.1 批处理与分时
1950 年代,计算机以批处理方式运行:操作员收集一批打孔卡作业,依次运行,输出结果。批处理最大化硬件利用率,但交互性为零——用户无法在程序运行中干预。

1960 年代,分时系统(如 CTSS、Multics)出现:CPU 在多个用户终端间快速切换,每个用户感觉独占整机。分时系统首次实现:

进程概念:程序运行的一个实例,拥有独立状态

调度:按时间片轮转分配 CPU

内存隔离:每个进程拥有独立地址空间

分时系统的三个思想——进程、调度、隔离——至今仍是所有操作系统(含 Gvtcier)的基石。

4.2 UNIX:简洁的哲学
1969 年,肯·汤普森与丹尼斯·里奇在贝尔实验室开发 UNIX。UNIX 的哲学是"小而美":

一切皆文件

每个程序做好一件事

程序间通过管道组合

UNIX 用 C 语言重写(1973 年),实现了"操作系统可以用高级语言编写"的突破——这对 Gvtcier 意义重大:Gvtcier 同样以高级语言(Rust)编写内核,而非纯汇编。

4.3 POSIX:标准的统一与垄断
1980 年代,UNIX 分裂为多个商业与学术分支(BSD、System V、Linux…),接口互不兼容。为统一接口,IEEE 制定 POSIX 标准(Portable Operating System Interface):

定义进程、线程、文件、信号、套接字等接口

目标:程序在不同 UNIX 系统间可移植

POSIX 的积极面是标准化;但它同时成为事实垄断:全球操作系统(包括大量"国产"系统)以兼容 POSIX 为第一要务,接口形态、进程模型、文件语义全部沿用他人定义。这正是 Gvtcier 诞生的背景——详见第三卷。

4.4 小结
批处理最大化利用率,分时带来进程、调度、隔离

UNIX 以简洁哲学与高级语言重写开创现代内核

POSIX 统一了接口,却也固化了垄断——为自研操作系统留下空间

第一卷结语:从算盘到 POSIX,计算机完成了"记录 → 计算 → 程序 → 操作系统 → 标准"的五级跃迁。下一卷深入内核内部,讲解每一级跃迁背后的技术原理。

第二卷 操作系统内核原理
本卷以 Gvtcier 的实现为参照,系统讲授操作系统内核的八大主题:内核本质、引导、内存、任务进程、通信安全、文件存储、设备中断、网络。每章先讲原理,再对照 Gvtcier 的具体实现。

第 5 章 内核的本质
5.1 内核是什么
内核是操作系统在计算机上最早启动、常驻内存、管理全部硬件资源并向外提供服务的程序。用户程序无法直接操作硬件,必须经由内核。

内核的四项基本职责:

职责	说明
资源管理	分配/回收 CPU 时间、内存、磁盘、设备
抽象服务	把硬件细节封装为易用接口(文件、进程、套接字)
隔离保护	防止程序互相干扰与破坏内核
调度仲裁	决定哪个程序何时使用哪个资源
5.2 特权级:内核态与用户态
x86-64 提供 4 个特权级(ring 0-3),操作系统通常只用两级:

内核态(ring 0):可执行全部指令(修改页表、关中断、访问所有内存)

用户态(ring 3):受限指令集,访问自己的地址空间

两者通过段选择子中的 RPL(请求特权级)与 CPL(当前特权级)区分。Gvtcier 的 GDT 定义内核代码段(ring 0)与用户代码段(ring 3),任务切换时通过 TSS 记录内核栈顶(RSP0)。

5.3 系统调用:用户态进入内核的通道
用户程序需要内核服务时,执行系统调用。x86-64 提供 syscall 指令:

syscall 指令
  → CPU 切换到内核态,跳转 LSTAR(MSR 0xC0000082)指向的入口
  → 保存用户返回地址到 rcx,rflags 到 r11
  → 内核按 rax 中的调用号分发到具体服务
  → 完成后 iretq/sysret 返回用户态
Gvtcier 的系统调用约定:

项	约定
调用号	rax
参数	rdi、rsi、rdx、r10、r9、r8
返回	写回 SYS_RET,由 ABI 层封装读取
范围	1-40 号,越界忽略
5.4 内核职责在 Gvtcier 中的映射
原理职责	Gvtcier 实现
资源管理	Buddy/堆分配器、调度器、位图
抽象服务	GvFAT 文件、IPC 端点、Gvinter 网络
隔离保护	页表、权能、用户/内核态
调度仲裁	时间片轮转、动态优先级
第 6 章 引导过程
6.1 固件与引导的两条路径
计算机上电后,CPU 从固定地址取指,执行固件(BIOS 或 UEFI)。固件负责最基本的硬件初始化,然后把控制权交给操作系统引导层。

Gvtcier 支持两条引导路径,最终汇合于同一内核入口:

BIOS 路径:boot.asm(16 位) → stage2.asm(读 FAT12 找 KERNEL.GCX)
           → pm32(32 位保护模式加载 gcx 段) → 建页表 → lm64(64 位)
UEFI 路径:固件直接加载 bootloader.efi → 读 gcx → 进入内核
6.2 实模式到长模式:引导的阶梯
x86 CPU 启动时处于实模式(16 位,1MB 寻址),须逐级升格到长模式(64 位):

实模式(16 位)
  → 开 A20 地址线
  → 加载 GDT → 切换保护模式(32 位)
  → 置 CR4.PAE(物理地址扩展)
  → 写 EFER.LME → 置 CR0.PG 开启分页
  → 长模式(64 位)
Gvtcier 的 stage2.asm 完整实现这一阶梯:实模式读盘、保护模式加载 gcx 段、建 PML4 页表、跳长模式。

6.3 内存探测:e820 与 BootInfo
引导层必须告诉内核"哪些物理内存可用"。BIOS 提供 e820 中断(int 0x15,功能 0xE820)枚举内存区域:

eax=0xE820, edx=0x534D4150("SMAP")
每次调用返回一段区域(start, len, type)
循环直到 ebx==0
Gvtcier 将探测结果整理为 MemoryRegion 数组,连同帧缓冲信息封装成 BootInfo 结构传给内核入口。内核据此初始化 Buddy 分配器——见下一章。

6.4 内核格式:gcx
引导层加载的是 gcx 格式(魔数 0x786367),而非 ELF。gcx 段表显式给出"文件偏移 + 虚拟地址 + 大小",引导层按表复制:

物理地址 = 段虚拟地址 − 虚拟基址(KERNEL_VIRT)
内存大小 > 文件大小的部分清零(BSS 归零)
跳转入口地址
第 7 章 内存管理
7.1 物理内存与虚拟地址空间
内存管理回答两个问题:物理页谁在用、程序看到什么地址。

物理内存:真实 RAM,按 4KB 页组织

虚拟地址空间:每个进程看到独立的地址范围,经页表映射到物理页

x86-64 虚拟地址空间按最高位划分:

0x0000_0000_0000_0000 ── 用户态(低半区)
0xFFFF_8000_0000_0000 ── 内核态(高半区,KERNEL_VIRT)
内核位于高半区:用户程序无法访问该范围,天然隔离;且高半区对所有进程共享,内核页表只需映射一次。

7.2 页表:四级查找
x86-64 使用 4 级页表(PML4 → PDPT → PD → PT → 页),每级 512 项,按虚拟地址的 9 位索引逐级下钻:

虚拟地址分解:47:39 PML4 | 38:30 PDPT | 29:21 PD | 20:12 PT | 11:0 偏移
每项页表项(PTE)含物理地址与标志位:present(存在)、writable(可写)、user(用户可访问)等。

Gvtcier 的 Paging 模块实现 map_page/unmap_page/page_phys,并在异常处理中响应缺页。

7.3 物理分配器:Buddy 与堆
内核需要高效分配物理页。Buddy 分配器按 2 的幂次合并空闲块:

分配 order=n:找最小可用块 → 二分拆分到大块
释放:与相邻同阶空闲块合并(伙伴合并)
Gvtcier 的 Buddy 阶数按内存总量自动推导;其上再叠加堆分配器(变长分配),相邻空闲块前后向合并,容量按内存 1/4 自动推导(封顶 64MB)。

7.4 虚拟内存与加固
写时复制(CoW):任务栈页共享零页,首次写入触发缺页复制,降低内存占用

KASLR:内核虚拟基址随机偏移(页对齐),提高攻击难度

守护页:用户栈底一页不映射,向下溢出触发缺页异常

页表加固:遍历深度上限、地址对齐校验、OOM 错误返回

NOTE:这些加固手段的目标是"程序出错不破坏系统"——这正是第 5 章隔离职责的具体化。

第 8 章 任务与进程
8.1 进程、任务与线程
进程:资源分配的载体(地址空间、权能)

任务:可调度的执行单元,是内核调度的最小单位

线程:进程内并发的执行流

Gvtcier 中,"任务"与"进程"是分层概念:任务表(TASKS)记录可调度单元,进程表(PROCESSES)记录权能与父子关系。内核线程(kthread_create)则是内核态的任务,不进入用户空间。

8.2 调度:谁先运行
调度器决定就绪任务中谁获得 CPU。Gvtcier 采用时间片轮转 + 优先级:

APIC 定时器每 100 tick 触发一次调度
  → 遍历就绪任务,选优先级最高者
  → 运行中任务优先级递减(防霸占)
  → 阻塞任务优先级递增(防饥饿)
调度点有二:定时器中断(抢占式)与任务主动让出(yield)。

8.3 上下文切换
上下文切换保存当前任务的全部寄存器,恢复下一个任务的寄存器:

asm_switch(&当前.context, &下一个.context)
  → 保存 rax..r15、rsp、rip 到当前任务上下文
  → 恢复下一个任务上下文 → 继续执行
切换时同步更新:CR3(页表,隔离地址空间)、TSS 的 RSP0(内核栈顶,供中断使用)。

8.4 进程模型:裂变
Gvtcier 的进程创建采用裂变(fission),而非传统 fork:

维度	fork	裂变
地址空间	完整复制父进程	新建独立映像
权能	继承全部	创建时显式定义
代价	复制全部页表与内存	仅加载新映像
裂变流程:syscall 38 传入映像与权能定义 → 内核分配页表、加载 ELF、映射用户栈(CoW 零页)、设置权能、登记父子关系。

第 9 章 通信与安全
9.1 IPC:端点消息
进程间通信(IPC)是系统协作的基础。Gvtcier 采用端点(endpoint)消息模型:

发送方 ──shout(端点, 消息)──▶ 端点队列 ◀──listen(端点)── 接收方
每个端点维护环形队列(64 槽),消息 32 字节

发送/接收依赖权能校验(SEND/RECV 权限位)

接收可阻塞(block_on)或非阻塞;发送方唤醒等待者(wake_on)

9.2 权能:访问控制的载体
权能(capability)是对资源(端点等)的受控引用。任务持有权能表,每项含对象类型、对象 ID、权限位:

权限位	含义
RIGHT_SEND	允许向该端点发送
RIGHT_RECV	允许从该端点接收
权能在进程创建时定义,运行期不可变更——资源访问范围由"出生时的定义"决定,这是最小权限原则的体现。

9.3 同步原语
自旋锁(Spinlock):忙等互斥,适合临界区极短的场景,记录持有者

信号量(Semaphore):计数同步,sem_wait 计数不足时阻塞,sem_post 唤醒

条件变量(Condvar):等待条件满足,cv_wait 阻塞、cv_notify 唤醒

软件定时器:基于 tick 的定时唤醒(timer_set/poll)

信号机制:signal_send 向任务投递信号,SIG_TERM 终止任务

第 10 章 文件与存储
10.1 块设备与文件系统分层
存储从底层到上层分四层:

应用(syscall 打开/读写)
  → 文件系统(GvFAT:目录树/位图/元数据)
  → 块设备驱动(AHCI/ATA:48 位 LBA)
  → 磁盘(512B 扇区)
Gvtcier 的 GvFAT 位于此分层中,管理逻辑结构;AHCI 驱动负责物理读写。

10.2 GvFAT 布局
块 0      超级块(魔数 GvF + 布局参数)
块 1..    位图区(每块 1 位)
..        根目录区(固定 32 块)
..        数据区(连续块分配)
位图:标记数据块占用,fsck 依此校验一致性

目录项:40 字节(文件名 12 + 起始块 8 + 大小 8 + 块数 4 + 属性 1 + 时间戳 4 + 属主/属组 2),时间戳秒级

路径解析:按 / 分割逐级下钻,符号链接最多跳 4 次防环

10.3 写入与健壮性
按需扩展:写满时新分配 = 需求 + 8 块(预分配),数据先复制再释放旧块

批量读取:一次最多读 8 块,减少系统调用

fsck:遍历目录跟踪引用块,对比位图,报告孤儿块与丢失块

文件锁:lock/unlock 互斥读写

多盘挂载:mount(base_lba) 以偏移挂载多块盘

第 11 章 设备与中断
11.1 中断:硬件通知内核的方式
CPU 无法一直轮询硬件,硬件通过中断主动通知内核。x86-64 的中断控制器体系:

LAPIC(每核本地中断控制器,0xFEE00000)
  ├─ 定时器中断(时间片/软件定时器)
  └─ 本地中断
IOAPIC(系统级中断控制器,0xFEC00000)
  ├─ 键盘(IRQ1)、鼠标(IRQ12)等外设中断
  └─ 转发到指定核的 LAPIC
中断经 IDT(中断描述符表) 分发:每个向量对应一个处理函数入口。Gvtcier 的 IDT 为异常(0-31)与设备中断(定时器 32、键盘 33、鼠标 44)设置入口。

11.2 中断处理流程
外设触发中断
  → IOAPIC 转发到 LAPIC → CPU 压栈帧(向量/错误码/寄存器)
  → 查 IDT → 跳处理函数
  → 处理(读设备寄存器、置 EOI) → iretq 返回
Gvtcier 的 rust_irq_handler 按向量分发:定时器触发调度与软件定时器,键盘/鼠标读 PS/2 端口并封装为 IPC 消息投递。

11.3 PCI:设备发现
PCI 总线是系统设备的发现机制。内核通过配置空间(地址端口 0xCF8/数据端口 0xCFC)枚举设备:

写地址端口(总线/设备/功能/寄存器)
  → 读数据端口得到 16 位厂商 ID 与设备 ID
  → 遍历 32 设备 × 8 功能
  → 读取 BAR(基地址寄存器)定位设备 I/O 或内存窗口
Gvtcier 的 Device 模块实现 PCI 枚举(多函数、IRQ、BAR),并提供热插拔检测:周期性重扫对比设备表,报告新增/移除。

11.4 驱动模型
Gvtcier 采用用户态驱动模型:驱动是独立任务,不直接驻留内核地址空间,通过 IPC 端点与内核通信:

硬件 ←─寄存器/端口─ 驱动任务(用户态)
  │                    │
  └──── IPC 端点消息 ──┘ 内核(仲裁/隔离)
驱动按能力注册(CAP_FAT/CAP_GPU/CAP_AUDIO),内核与用户经端点收发消息。

第 12 章 网络协议栈
12.1 分层的必要性
网络协议按职责分层,每层只处理自己的字段,层间通过接口协作:

应用层      DNS / HTTP / DHCP / 套接字
传输层      TCP(可靠字节流) / UDP(不可靠数据报)
网络层      IPv4 / IPv6(寻址与转发)
链路层      ARP(地址解析) / 以太网帧
硬件层      网卡(如 RTL8139)
12.2 收包与发包路径
Gvtcier 的 Gvinter 驱动轮询网卡环形缓冲收包:

收包:poll() 读环形缓冲 → 按以太网类型分发(ARP/IPv4/IPv6)→ 逐层解析
发包:上层构造载荷 → 查 ARP 缓存定目标 MAC → 封装以太网帧 → 写网卡
12.3 TCP:可靠传输的核心机制
TCP 在不可靠的 IP 之上提供可靠字节流,核心机制:

三次握手:SYN → SYN-ACK → ACK 建立连接

序号与确认:每字节有序号,接收方确认已收序号

重传:超时未确认则重发(SYN 最多 3 次)

拥塞控制:慢启动(指数增长)→ 拥塞避免(线性增长)→ 超时减半窗口

连接表:多路复用,每条连接独立维护序号与窗口

FIN 状态机:四次挥手关闭连接

12.4 地址解析:ARP 与 NDP
ARP(IPv4):IP → MAC 映射,发送前查缓存(8 条),未命中广播请求,应答自动学习

NDP(IPv6):邻居请求 NS / 邻居通告 NA,以及 RA 网关学习

12.5 应用层服务
DNS:域名 → IP 查询(UDP 53)

DHCP:动态获取 IP(DISCOVER/OFFER/REQUEST/ACK)

HTTP:客户端(GET 请求)与服务器(响应 HTML)

原始套接字:帧级收发,供协议调试与自定义协议

第二卷结语:八大主题构成内核的完整图景——引导建立环境,内存提供舞台,调度分配时间,IPC 连接进程,文件持久数据,中断驱动设备,网络连通世界。下一卷讲述为何要自研这一切。

第三卷 Gvtcier 的诞生
本卷回答一个根本问题:在一个 POSIX 统治全球操作系统的时代,Gvtcier 为什么选择自研接口、拒绝兼容?这既是技术选择,也是接口主权的选择。

第 13 章 标准与垄断
13.1 POSIX 的由来
1980 年代,UNIX 分裂为 BSD、System V、AIX、HP-UX 等众多分支,接口互不兼容。程序在 A 系统上编译,在 B 系统上可能无法运行。为统一接口,IEEE 发起 POSIX(Portable Operating System Interface)标准:

目标:程序跨 UNIX 系统可移植

内容:进程、线程、文件、信号、套接字等接口的统一定义

结果:成为事实上的操作系统接口标准

POSIX 的初衷是"可移植性"——这本无可厚非。

13.2 从标准到垄断
然而,标准在演进中固化为垄断。半个多世纪以来,全球操作系统的接口形态惊人地一致:

维度	被 POSIX 固化的形态
进程模型	fork/exec,复制地址空间
通信	信号、管道、System V IPC
文件	以 POSIX 权限位为核心的目录树
线程	pthread 线程模型
网络	socket 套接字
问题不在 POSIX 本身,而在依赖:

新系统把"兼容 POSIX"当作第一优先,接口形态、进程模型、文件语义全部沿用他人定义

接口即生态:一旦开发者熟悉 POSIX,替代系统的门槛被无限抬高

所谓"国产系统"大多仍是 POSIX 的再实现——外壳换新,内核照旧

13.3 接口主权:为什么不能只有一种声音
接口是操作系统的"宪法"。接口主权意味着:进程怎么创建、消息怎么传递、文件怎么组织、字符怎么编码——这些基础规则由自己定义,而非由外部标准决定。

自主接口的价值:

技术自由:可以按需求重新设计,不被历史包袱束缚

安全可控:接口细节完全透明,无隐藏依赖

生态自主:应用围绕自有接口生长,而非寄生他人标准

第 14 章 接口主权:Gvtcier 的立场
14.1 从零开始的自研体系
Gvtcier 的立场是从零定义接口,而不是再实现一个 POSIX。对照第二卷的八大主题,Gvtcier 给出自己的答案:

主题	POSIX 形态	Gvtcier 形态
进程创建	fork(复制地址空间)	裂变(新建独立映像,显式权能)
进程通信	信号/管道/System V	端点消息 + 权能
文件系统	POSIX 权限位	GvFAT(自制目录项/位图/元数据)
字符编码	ASCII/UTF-8 默认	Gv-2280(自制编码,GB2312 兼容)
编程语言	C/POSIX 生态	GvtcierC(自制语言与工具链)
版本控制	git	Gvt(自制版本工具)
调试验证	gdb/qemu	GvtcierXuNiJi(最小虚拟机 + GvDebug)
14.2 每个子系统都是独立的答案
Gvtcier 不是"换皮 Linux",而是逐个子系统的重新回答:

裂变:不复制地址空间,新建映像 + 创建时定义权能,资源范围由出生决定

端点消息:以权能校验的端点替代信号与管道,消息经环形队列传递

GvFAT:超级块 + 位图 + 目录项的自制布局,秒级时间戳、fsck、多盘挂载

Gv-2280:单字节字母区 + 双字节汉字区的自制编码,与 GB2312 汉字一一对应

14.3 完全自持的工具链
接口自研不止于内核,还包括整个开发生态:

GvtcierC(gvtcierc + gvtcierk)── 语言与编译链,不依赖 gcc
Gvt ── 版本控制,不依赖 git
GvtcierXuNiJi ── 最小虚拟机,不依赖 QEMU
GvFont ── 点阵字体工具
一个开发者可以在不接触任何外部工具链的前提下,完成内核开发、驱动编写、应用构建与验证。

15.1 核心理念:接口由使用者定义

自研优先:每个子系统都从第一性原理重新设计,而非移植

第 17 章 引导扇区：第一行代码
17.1 BIOS 引导过程
计算机通电后，BIOS 固件完成自检，然后读取磁盘的第一个扇区（512 字节）到内存地址 0x7C00，检查最后两字节是否为 0x55 0xAA（魔数）。若是，则跳转到 0x7C00 执行。这 512 字节就是我们的“引导扇区”。

CAUTION：整个引导扇区只有 512 字节！代码、数据、魔数全部挤在里面。超过 510 字节会导致魔数被覆盖，BIOS 拒绝引导。

17.2 写一个最小的引导扇区
在 boot/boot.asm 中写入以下代码：

[org 0x7C00]           ; 告诉汇编器，代码将被加载到 0x7C00
[bits 16]              ; BIOS 启动时处于 16 位实模式

start:
    ; 清屏（用 BIOS 中断 0x10）
    mov ax, 0x0003
    int 0x10

    ; 在屏幕上打印 'A'
    mov al, 'A'
    mov ah, 0x0E        ; 功能号：Teletype 输出
    int 0x10

    ; 死循环（让 CPU 停在这里）
    cli
    hlt
    jmp $

    ; 填充至 510 字节，最后两字节为引导魔数
    times 510 - ($ - $$) db 0
    dw 0xAA55
17.3 编译与运行
nasm -f bin boot/boot.asm -o boot/boot.bin
此时 boot.bin 是一个 512 字节的裸二进制文件。我们直接用 QEMU 加载：

qemu-system-x86_64 -drive format=raw,file=boot/boot.bin
屏幕左上角应该出现一个白色的 A，然后系统挂起。恭喜，你已成功运行了第一个“操作系统”！

17.4 踩坑记录
陷阱一：org 0x7C00 必须写对。若写成 org 0x0，汇编器计算的地址偏移会错位，导致跳转失败。

陷阱二：最后两字节必须是小端序 0xAA55。若写成 0x55AA 或漏写，BIOS 不认。

陷阱三：在 Windows 下用记事本保存，可能加入 BOM 头或换行符为 CRLF，NASM 可能报错。建议用 VS Code 并设置换行符为 LF。

第 18 章 进入保护模式
18.1 实模式的局限
16 位实模式只能访问 1MB 内存，且没有特权级隔离。要发挥 CPU 的全部能力，必须切换到保护模式（32 位）。保护模式提供 4GB 寻址空间、分段机制和特权级。

切换需要三步：

加载全局描述符表（GDT），定义代码段和数据段的基址与权限。

设置控制寄存器 CR0 的保护模式位（PE）。

执行一个远跳转，清空指令流水线，进入 32 位代码段。

18.2 代码实现
在 boot.asm 末尾追加以下内容：

; 加载 GDT
lgdt [gdt_descriptor]

; 开启保护模式
mov eax, cr0
or eax, 1
mov cr0, eax

; 远跳转到 32 位代码段（偏移 0x08 是 GDT 中代码段的选择子）
jmp 0x08:protected_mode

[bits 32]
protected_mode:
    ; 现在处于 32 位保护模式
    mov ebx, 0xB8000    ; 文本模式显存地址
    mov byte [ebx], 'P' ; 直接写显存
    mov byte [ebx+1], 0x0F ; 属性：白字黑底
    cli
    hlt

; GDT 定义（放在文件末尾）
gdt_start:
    ; 空描述符（必须存在）
    dq 0x0
gdt_code:
    ; 代码段：基址 0，长度 4GB，可读执行
    dw 0xFFFF    ; 段限 0-15
    dw 0x0       ; 基址 0-15
    db 0x0       ; 基址 16-23
    db 0b10011010 ; 访问字节（Present, Ring0, 代码段）
    db 0b11001111 ; 标志 + 段限 16-19
    db 0x0       ; 基址 24-31
gdt_data:
    ; 数据段：基址 0，长度 4GB，可读写
    dw 0xFFFF
    dw 0x0
    db 0x0
    db 0b10010010 ; 数据段，可读写
    db 0b11001111
    db 0x0
gdt_end:

gdt_descriptor:
    dw gdt_end - gdt_start - 1  ; 表长度 - 1
    dd gdt_start                ; 表基址
18.3 运行与观察
重新编译并运行：

nasm -f bin boot/boot.asm -o boot/boot.bin
qemu-system-x86_64 -drive format=raw,file=boot/boot.bin
你应该先看到 A（实模式打印），然后很快看到 P（保护模式直接写显存）。如果只看到 A，说明保护模式切换失败。

18.4 踩坑记录
陷阱一：远跳转 jmp 0x08:protected_mode 中的 0x08 是 GDT 代码段的选择子，它等于 gdt_code 在 GDT 中的偏移。因为第一个描述符（空描述符）占 8 字节，所以代码段选择子是 0x08。如果 GDT 布局变化，这个值必须同步修改。

陷阱二：GDT 中的 db 0b10011010 和 db 0b11001111 是二进制写法，有些老版本 NASM 不支持 0b 前缀，可以换成十六进制 0x9A 和 0xCF。

陷阱三：切换后，所有段寄存器（DS、ES、SS）仍然指向实模式的段，必须重新加载数据段选择子（mov ax, 0x10; mov ds, ax），否则内存访问会出错。

第 19 章 长模式：64 位的世界
19.1 从 32 位到 64 位
x86-64 的长模式将寻址能力提升到 64 位，并引入四级页表。进入长模式比进入保护模式复杂得多，需要：

在保护模式下，开启物理地址扩展（PAE）（CR4.PAE = 1）。

建立至少一级页表（PML4），并设置 CR3 指向它。

设置 EFER 寄存器（MSR 0xC0000080）的 LME 位。

开启分页（CR0.PG = 1）。

用远跳转进入 64 位代码段。

19.2 建立临时页表
在 32 位代码中，我们在内存中构造一个最小的页表，将前 2MB 物理内存映射到虚拟地址 0xFFFFFFFF80000000（高半区），这是内核惯用的加载地址。

; 在保护模式代码中，准备页表
; 我们使用 2MB 大页，简化映射
section .data
align 0x1000
pml4:
    dq 0x2003        ; 指向 PDPT（地址 0x2000，存在+可写）
    times 511 dq 0   ; 其余 PML4 项清零

pdpt:
    dq 0x3003        ; 指向 PD（地址 0x3000，存在+可写）
    times 511 dq 0

pd:
    ; 将 0-2MB 映射到高半区 0xFFFF800000000000 的对应位置
    dq 0x83          ; 低 2MB：物理地址 0x0，大页标志 0x80
    times 511 dq 0
然后在保护模式代码中加载页表：

; 将页表放在物理地址 0x1000（对齐）
mov eax, pml4
mov cr3, eax

; 开启 PAE
mov eax, cr4
or eax, 1 << 5
mov cr4, eax

; 设置 EFER.LME
mov ecx, 0xC0000080
rdmsr
or eax, 1 << 8
wrmsr

; 开启分页
mov eax, cr0
or eax, 1 << 31
mov cr0, eax

; 远跳转到 64 位代码段
jmp 0x08:long_mode
19.3 64 位代码
[bits 64]
long_mode:
    ; 此时已在长模式，可放心使用 64 位寄存器
    mov rax, 0xFFFF800000000000 + 0xB8000
    mov word [rax], 0x0F4C   ; 打印 'L'，白字黑底
    cli
    hlt
19.4 踩坑记录
陷阱一：页表必须放在 4KB 对齐的物理地址。若 pml4 未对齐，mov cr3, eax 会触发一般保护异常。

陷阱二：远跳转的选择子仍是 0x08，但此时 GDT 必须包含 64 位代码段描述符（在 GDT 中，代码段描述符的 L 位必须为 1）。

陷阱三：在开启分页后，EIP 仍然是 32 位值，必须在远跳转时指定 64 位段，否则 CPU 会认为仍在 32 位模式。

第 20 章 用 C 语言编写内核
20.1 为什么需要 C 语言
汇编语言编写大型内核极为低效。我们用 C 语言实现内核的主体部分，只需在引导层用汇编完成最底层的初始化。GCC 的 -ffreestanding 选项让 C 代码不依赖任何标准库，适合内核开发。

20.2 一个极简内核
新建 kernel/kernel.c：

void kernel_main(void) {
    // 直接写显存，在屏幕顶部打印 "Hello from C!"
    char* video_memory = (char*) 0xFFFF800000000000 + 0xB8000;
    const char* msg = "Hello from C!";
    int i = 0;
    while (msg[i] != '\0') {
        video_memory[i*2] = msg[i];
        video_memory[i*2 + 1] = 0x0F;  // 白字黑底
        i++;
    }
    // 死循环
    while(1);
}
20.3 编译与链接
编译 C 文件为目标文件（不链接标准库）：

gcc -ffreestanding -m64 -c kernel/kernel.c -o build/kernel.o
编写链接脚本 kernel/linker.ld，指定入口地址和内存布局：

ENTRY(kernel_main)
SECTIONS {
    . = 0xFFFF800000000000 + 0x100000;  /* 内核加载到高半区 1MB 处 */
    .text : {
        *(.text)
    }
    .data : {
        *(.data)
    }
    .bss : {
        *(.bss)
    }
}
链接：

ld -T kernel/linker.ld -o build/kernel.elf build/kernel.o
20.4 引导层加载 ELF
引导层需要解析 ELF 文件头，将代码段复制到指定的物理地址。为避免复杂化，我们退一步：先用 objcopy 将 ELF 转为纯二进制，然后引导层直接跳转。

objcopy -O binary build/kernel.elf build/kernel.bin
在引导层中，我们将 kernel.bin 加载到物理地址 0x100000（1MB 处），然后跳转过去。由于我们在长模式中已经建立了高半区映射，虚拟地址 0xFFFF800000100000 将指向物理地址 0x100000。

20.5 运行
将 kernel.bin 拼接到引导扇区之后（磁盘第二个扇区），用 QEMU 启动。屏幕顶部应该出现 “Hello from C!”。

20.6 踩坑记录
陷阱一：-m64 必须指定，否则 GCC 默认生成 32 位代码。

陷阱二：kernel.bin 不能有 BSS 段未清零，因为二进制文件不包含零初始化数据。引导层需要在加载后手动清零 BSS 区域。

陷阱三：链接脚本中的地址 0xFFFF800000100000 必须与页表映射一致。若映射的是 2MB 大页，地址需要对齐到 2MB 边界。

第 21 章 实现字符输出函数
21.1 封装显存操作
直接操作显存地址太原始。我们实现一个 putchar 函数，管理光标位置。

在 kernel/kernel.c 中添加：

static int cursor_x = 0, cursor_y = 0;
static char* video = (char*) 0xFFFF800000000000 + 0xB8000;

void putchar(char c) {
    if (c == '\n') {
        cursor_x = 0;
        cursor_y++;
        return;
    }
    int pos = (cursor_y * 80 + cursor_x) * 2;
    video[pos] = c;
    video[pos + 1] = 0x0F;
    cursor_x++;
    if (cursor_x >= 80) {
        cursor_x = 0;
        cursor_y++;
    }
}

void puts(const char* s) {
    while (*s) putchar(*s++);
}
然后修改 kernel_main 调用 puts("Hello from C!\nWelcome to my kernel.")。

21.2 滚动处理
当光标超出屏幕底部时，需将整屏上移一行：

void scroll() {
    if (cursor_y < 25) return;
    // 将第 1~24 行复制到 0~23 行
    for (int y = 1; y < 25; y++) {
        for (int x = 0; x < 80; x++) {
            int src = (y * 80 + x) * 2;
            int dst = ((y - 1) * 80 + x) * 2;
            video[dst] = video[src];
            video[dst + 1] = video[src + 1];
        }
    }
    // 清空最后一行
    for (int x = 0; x < 80; x++) {
        int pos = (24 * 80 + x) * 2;
        video[pos] = ' ';
        video[pos + 1] = 0x0F;
    }
    cursor_y = 24;
}
在 putchar 中调用 scroll。

21.3 踩坑记录
陷阱一：显存每字符占 2 字节（字符 + 属性），80*25*2 = 4000 字节。若写入越界，会破坏其他内存。

陷阱二：\n 只换行不回车。我们实现中已经将 cursor_x 置 0，所以是换行+回车。

陷阱三：滚动时使用 memcpy 会依赖标准库，我们用循环自行复制。

第 22 章 中断与键盘输入
22.1 设置 IDT
中断是内核与硬件交互的核心。我们设置键盘中断（IRQ1），当按键时打印扫描码。

首先，需要建立中断描述符表（IDT），在 kernel/idt.c 中：

struct idt_entry {
    uint16_t base_low;
    uint16_t selector;
    uint8_t  ist;
    uint8_t  flags;
    uint16_t base_mid;
    uint32_t base_high;
    uint32_t zero;
} __attribute__((packed));

struct idt_ptr {
    uint16_t limit;
    uint64_t base;
} __attribute__((packed));

void set_idt_entry(int vector, void* handler, uint8_t flags) {
    // 填充 IDT 条目，将 handler 地址拆分为低、中、高三段
}
22.2 键盘中断处理
在 kernel/isr.c 中用汇编写中断桩，调用 C 处理函数：

global keyboard_handler
keyboard_handler:
    push rax
    push rdi
    in al, 0x60           ; 读键盘扫描码
    mov rdi, rax
    call c_keyboard_handler
    pop rdi
    pop rax
    iretq
C 端打印扫描码：

void c_keyboard_handler(uint8_t scancode) {
    char hex[3] = "00";
    hex[0] = "0123456789ABCDEF"[scancode >> 4];
    hex[1] = "0123456789ABCDEF"[scancode & 0x0F];
    puts("Key: ");
    puts(hex);
    puts("\n");
}
22.3 开启中断
在 kernel_main 末尾：

// 初始化 PIC，启用键盘中断
outb(0x21, 0xFD);  // 仅启用 IRQ1
sti();             // 开中断
while(1);
22.4 踩坑记录
陷阱一：IDT 条目必须按 16 字节对齐，处理器要求 base 和 limit 字段正确，否则触发 #GP。

陷阱二：中断桩必须保存所有被破坏的寄存器，否则 C 函数返回时寄存器乱掉，导致崩溃。

陷阱三：outb 是 I/O 端口写入函数，需要内联汇编实现。GCC 不提供标准库的 outb。

25.1 源码地图
内核本体位于 Kernel/kernel/src/,按职责组织:

25.2 初始化顺序:读懂内核的钥匙
main.rs 的初始化顺序即内核的"生命线":

内存探测(BootInfo/e820)→ Buddy → 堆 → 页表 selftest → KASLR
→ GDT → IDT → SMEP → APIC 定时器 → syscall 入口
→ IPC 端点 → 音频 → AHCI → 网络(Gvinter)→ 裂变进程
→ 用户任务创建 → Shell
编辑内核时,新增子系统应在对应阶段接入,并保持"先依赖后使用"的顺序。

25.3 编辑内核的通用模式
新增一个功能通常涉及四步:

实现模块:新建或扩展 Kernel/kernel/src/ 下的模块

注册模块:在 main.rs 顶部 mod 声明

接入初始化:在初始化顺序的合适位置调用

编译验证:cargo build --release + 运行观察串口日志

CAUTION:内核代码运行于裸机,无标准库。字符串、分配、格式化等须用 core:: 或内核自有设施;不可使用 std::。

25.4 编码规范
新代码不写注释,与既有风格一致

接口命名使用拼音语义(如 gvfat_open、taojie_fasong)

保持模块单一职责,改动最小化

第 26 章 开发驱动与内核模块
26.1 驱动模型回顾
Gvtcier 的驱动是独立任务,经 IPC 端点与内核通信,而非驻留内核地址空间:

硬件 ←─寄存器/端口─ 驱动任务 ──IPC 端点消息──▶ 内核
驱动按能力注册(CAP_FAT/CAP_GPU/CAP_AUDIO),用户态程序可经内核查询驱动并收发消息。

26.2 以 GvFAT 驱动为例
GvFAT 驱动位于 Kernel/Drive/gvfat/,是文件系统驱动的范例:

GvFat.rs 实现全部文件操作(open/read/write/mkdir/remove…)

磁盘读写经 raw_disk_read/write(syscall)访问 AHCI

mount(base_lba) 支持多盘挂载

自带 11 个单元测试(目录树/元数据/fsck/多盘)

开发新驱动可对照该结构:独立 crate → 实现操作集合 → 单元测试 → 打包进镜像。

26.3 内核模块接入点
若新增的是内核内模块(非独立驱动),接入点通常为:

main.rs 初始化顺序 → 模块 init() → 提供接口给 syscall/其他模块
例如新增"统计模块"需:实现模块 → mod 注册 → 初始化调用 → 在 syscall 或 Shell 暴露接口。

27.3 调用内核接口
用户程序经系统调用访问内核服务(见 GVPIR 编号表)。GvtcierC 程序可经内置运行时调用文件、输出等接口;内核侧由 Sys 模块封装对应调用号。

典型开发流程:

编写 .gc 源文件 → gvtcierc 编译为 .s → gvtcierk 汇编链接为 .exe
→ 作为任务加载进内核(裂变/create_task)→ 经 syscall 访问内核服务
27.4 内置运行时
gvtcierk 链接时内嵌最小运行时:打印(DaYin)与文件读写函数。用户程序无需链接外部库。

第 28 章 调试与验证
28.1 串口日志:内核的窗口
内核启动与运行全程输出串口日志,是首要调试手段:

启动阶段:内存/页表/定时器/syscall 各步骤 selftest 结果

运行阶段:IPC、驱动、网络、任务创建的事件记录

异常/崩溃:EXCEPTION 现场(向量/rip/cr2)+ panic 寄存器转储

28.2 异常与崩溃解读
内核遇到未处理异常时输出现场信息:

EXCEPTION vec=14 err=0x0 rip=0xffff800000200304 cr2=0x7fffff8 mode=kernel
字段	含义
vec	异常向量(14=缺页、6=非法指令、13=一般保护)
rip	发生异常的指令地址(可对照内核符号)
cr2	缺页时出错的虚拟地址
mode	user/kernel,指示异常发生在哪一侧
panic 时输出全部通用寄存器快照(rax..r15 + cr2),用于定位现场。

28.3 GvtcierXuNiJi:最小虚拟机验证
GvtcierXuNiJi 是随仓库的最小虚拟机,验证内核的硬件交互逻辑:

AHCI 仿真:校验内核写入的 CLB/FIS/PRDT 是否符合 AHCI 规范,执行读盘并比对数据

网络仿真:验证 RTL8139 初始化序列与协议帧构造(ARP/ping/TCP/HTTP/DNS),检查校验和与字段

运行:GvtcierXuNiJi 目录下 cargo run --release
成功:AHCI 布局 ✓ 网络帧构造 ✓
失败:GvDebug 报告定位到具体步骤
GvDebug 提供监控点、操作轨迹、现场转储与调试报告,失败时精确指出卡在哪一步。

28.4 调试建议
先看启动日志:确认初始化到哪一步,缩小范围

区分阶段:引导问题看引导层汇编,内核问题看串口日志

用最小虚拟机:硬件交互问题优先用 GvtcierXuNiJi 验证,再上 QEMU

崩溃现场:panic 转储的 rip 对照内核符号定位函数

CAUTION:QEMU 在 Windows 上偶发证书/连接问题;硬件交互验证优先使用 GvtcierXuNiJi,可避免不必要的环境干扰。

第五卷结语:至此,你已从环境搭建走到独立开发——编辑内核、编写驱动、用 GvtcierC 构建应用,并在最小虚拟机中验证。Gvtcier 的开发闭环就此打通。
